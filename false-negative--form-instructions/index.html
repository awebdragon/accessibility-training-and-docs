Accessibility Test Example: Form Instructions and Error Messages

A field can have a valid label and still fail users - by not indicating it is required, by omitting format instructions, or by showing error messages that have no programmatic association with the field that triggered them. Automated scanners check that labels exist, not that they are sufficient.

Example 1: Required field

Broken: No indicator that the field is required. The error message ("This field is required") is injected on submit but not associated with the input. A scanner sees a valid label and passes.

Fixed: aria-required="true" tells assistive technology the field is required before the user submits. The asterisk is decorative (aria-hidden="true"). The error is pre-connected via aria-describedby so when it appears, screen readers announce it. The error message names the field ("Full name is required") rather than just saying "This field is required".

Example 2: Format instructions

Broken: The hint text is visible but has no id and is not linked to the input. The error ("Invalid entry") gives no guidance on how to fix the problem. Both the hint and error are injected or visible in the DOM but programmatically invisible to screen readers.

Fixed: The hint has an id and is referenced in aria-describedby, so screen readers announce it when the field is focused. The error ("Invalid format. Expected: two letters followed by six digits, e.g. AB123456") points back to the existing instructions. To trigger: enter anything that does not match two letters followed by six digits.

Example 3: No instructions - error must carry the format

Broken: No format instructions on the field. The error message ("Invalid phone number") appears when an invalid number is entered but does not tell the user what a valid number looks like. To trigger: enter 111-1111 and submit.

Fixed: A persistent hint provides the format before the user types. The error message ("Invalid phone number. Expected format: 555-867-5309") includes the format so the user can correct their input even after the hint scrolls out of view. To trigger the error state: enter 111-1111 and submit.

Example 4: Placeholder-only instructions

Broken: The label is vague ("Number") and the only format guidance is in the placeholder, which disappears as soon as the user starts typing. The error ("Invalid number") gives no hint about the correct format. To trigger: enter 111-1111 and submit.

Fixed: The label is specific ("Phone number"), which alone provides enough context that a separate hint line is not needed. Because there is no persistent hint, the error message carries the format example ("Invalid phone number format. Input should look like: 555-867-5309"). To trigger: enter 111-1111 and submit.
